# gitbello — architecture and plan

Status: **planning** · Owner: Caleb · Budget: ~20 h/week · Workflow: milestone by milestone with review

---

## 1. Vision and scope

gitbello is a lightweight, native-feeling Git GUI for people who juggle many repositories and worktrees every day. Its main differentiators over GitHub Desktop and Fork are:

- **Repos and worktrees as first-class citizens.** Each repo opens in a tab, its worktrees sit in a strip of chips inside that tab, and live status shows everywhere.
- **A clean, uncluttered UI.** Balanced density, big simple buttons for the main features that lead to the detailed actions, keyboard-friendly, with a command palette for everything.
- **Better workflows** for merge (conflict preview before merging), shelving changes (stash without the stack) and new-task creation.
- **Light editing.** Edit the working copy directly from the diff viewer.
- **Fast and idle-quiet.** Native Rust core and a Godot UI that redraws only when needed.

### In scope (v1)

File, hunk and line selection for commits · commit and amend · fetch, pull and push · branches · tags · stash (as shelves) · history graph · diff viewer with editing · blame and file history · conflict resolver · cherry-pick · worktrees (chip strip, new task, path convention, cleanup) · command palette · live status badges and auto-fetch · custom actions · undo via operation log · integrated terminal (late milestone).

### Out of scope (v1)

GitHub, GitLab or any hosting integration (gitbello is pure git) · interactive rebase · submodule management (display only) · LFS management (it works transparently through git) · bundled git · auto-update.

## 3. Architecture

### 3.1 Layers

```
┌──────────────────────────────────────────────────────────┐
│ Godot (typed GDScript)                                   │
│  App shell · tabs · worktree chips · ActionRegistry      │
│  Custom controls: VirtualList, GraphView, DiffView       │
└──────────────▲──────────────────────────┬────────────────┘
               │ signals (events)         │ #[func] calls
┌──────────────┴──────────────────────────▼────────────────┐
│ gitbello-gdext (cdylib) — type conversion only           │
│  RepoSession (Node) · AppCore (singleton) · converters   │
└──────────────▲──────────────────────────┬────────────────┘
               │ Event channel            │ Rust API
┌──────────────┴──────────────────────────▼────────────────┐
│ gitbello-core (pure Rust)                                │
│  JobScheduler · RepoState · Watcher · GraphIndex         │
│  Operations (stage, commit, fetch…) · OpLog · Config     │
│  GitBackend trait → CliBackend (→ GixBackend later)      │
│  GitRunner (process spawning, env, parsing helpers)      │
└──────────────────────────────────────────────────────────┘
```

`gitbello-cli` links `gitbello-core` directly for headless testing and debugging.

### 3.2 GitRunner

There is one place that spawns git processes. Every call goes through it.

- It resolves the git binary once (PATH, plus an override in settings), runs `git --version`, and refuses to open repos if the version is below the minimum.
- **Environment** for every call:
  - `GIT_TERMINAL_PROMPT=0`
  - `GIT_OPTIONAL_LOCKS=0` for read jobs
  - `LC_ALL=C` and `LANG=C` so error parsing is stable
  - `GIT_PAGER=cat`
  - a no-op `GIT_EDITOR` to guard against stray editor launches
- **Global flags:** `-c core.quotepath=false -c color.ui=false`. Use `-z` output formats wherever git supports them.
- **Windows:** set `CREATE_NO_WINDOW` (0x08000000) through `CommandExt::creation_flags`.
- **Streaming mode** for long output (log, diff): it reads stdout incrementally. **Progress mode** for fetch, pull and push: it parses `--progress` lines from stderr into progress events.
- **Cancellation:** each running process is tied to a `CancelToken` and is killed on cancel.
- **Errors:** each call returns a `GitError { command, exit_code, stderr, kind }`, where `kind` is classified (auth failed, non-fast-forward, conflict, lock exists, not a repo, and so on) so the UI can offer specific fixes.
- **Logging:** every command, its duration and exit code go into an in-app "Git log" panel. This helps both debugging and user trust.

### 3.3 Backend and models

`GitBackend` is a trait with read operations (status, refs, worktrees, log stream, diff, blame, show, stash list, merge preview) and write operations (stage patch, commit, checkout, branch ops, fetch/pull/push, stash ops, worktree ops, cherry-pick, merge, conflict resolution). `CliBackend` implements all of it.

The main parsing sources are:

| Data | Command |
|---|---|
| Status | `git status --porcelain=v2 -z --branch --show-stash` |
| Refs | `git for-each-ref --format=...` with NUL-separated fields (includes upstream, ahead/behind via `%(upstream:track)`) |
| Worktrees | `git worktree list --porcelain -z` |
| Log | `git log --all --topo-order -z --format=%H%x1f%P%x1f%an%x1f%ae%x1f%at%x1f%s` (streamed) |
| In-progress operation | presence of `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REBASE_HEAD` and `rebase-merge/` in the git dir (`git rev-parse --git-dir`, `--git-common-dir`) |

Models (`RepoStatus`, `FileChange`, `Ref`, `Worktree`, `Commit`, `Hunk`, `StashEntry`, `OperationState`) are plain Rust structs in core. gdext converts them to `Dictionary` or packed arrays only at the boundary.

### 3.4 Jobs and events

- `JobScheduler` runs a small pool of worker threads (std threads, `Mutex` + `Condvar` queue and an `mpsc` event channel; no async runtime or extra crates).
- Each repo has a **write queue** (FIFO, one at a time). Reads run on the shared pool. A read that would race with a queued write waits until the write is done.
- Jobs report `Started`, `Progress`, `Finished(Result)` and `Cancelled` through one `Event` channel per `AppCore`.
- After any write, the scheduler automatically queues a targeted refresh. For example, a commit refreshes status, refs and the graph head; staging refreshes only status and the affected diff.
- **Coalescing:** duplicate pending refreshes of the same kind collapse into one.

### 3.5 Godot boundary

- `AppCore` is an autoload singleton. It owns the core runtime, drains the event channel in `_process`, and routes events to the right `RepoSession`.
- `RepoSession` is a Node, one per open worktree. A repo tab creates the session of its selected worktree chip first and the others when their chip is first selected; chip badges come from the worktree badges, which need no session. It exposes:
  - **Queries** returning small data: `status()`, `refs()`, `worktrees()`, `operation_state()`.
  - **Slice queries:** `graph_row_count()`, `graph_rows(start, count)` (commit fields plus lane data), and `diff_lines(file_id, start, count)`.
  - **Commands** that return a job id: `stage_hunk(...)`, `commit(...)`, `fetch()`, and so on.
  - **Signals:** `status_changed`, `refs_changed`, `graph_changed(range)`, `job_progress(id, pct, text)`, `job_finished(id, ok, error_dict)`.
- When nothing is changing, `_process` should do almost nothing. The event drain is a cheap `try_recv` loop.

### 3.6 Watching and refresh

- Use `notify` with gitbello's own per-repository debouncer (250 ms quiet, 1 s at most) on each open worktree directory and its git dir. Watch the common dir for refs.
- Ignore `objects/` churn and any path git would ignore. Status does the real work, and the watcher only decides whether a status refresh is needed.
- **Window focus in** (`NOTIFICATION_APPLICATION_FOCUS_IN`) triggers a cheap refresh of the active tab as a reliable fallback.
- **Auto-fetch:** a configurable interval (default 10 min, off for metered connections later). It runs with `--prune`, staggered across repos, and never runs while a write is in progress.

### 3.7 Godot app structure and settings

- **Project settings:**
  - `application/run/low_processor_mode = true`
  - HiDPI enabled
  - native file dialogs on
  - the untyped-declaration GDScript warning set to **error**
  - a sensible minimum window size
- **Custom controls** (in `godot/ui/`):
  - **`VirtualList`:** draws only visible rows with `_draw()`, handles selection, keyboard navigation, multi-select and context menus. It is the base for the commit list, file lists and the blame gutter.
  - **`GraphView`:** draws lanes and nodes for visible rows from the lane data supplied by core. It is combined with the commit list inside one scroll container.
  - **`DiffView`:** unified and side-by-side views with hunk and line selection gutters, intra-line highlights, and an editable working-copy side (§3.10). It wraps `CodeEdit` where possible. A minimap rendered by core replaces its scroll bar (M7.6).
  - **`AutoScroll`:** browser-style middle-click autoscroll for every `VirtualList` and `ScrollContainer` (M7.6).
- **`ActionRegistry`** (autoload). Every action is `{ id, label, category, shortcut, enabled: Callable, run: Callable }`. The command palette fuzzy-searches it, the menu bar, big buttons, menus and context menus are built from it, and shortcuts are rebindable. From M6.5 an action can also give the reason it is disabled (shown in tooltips), and a run carries its origin control so the job's progress shows there (§4 Feedback).
- **Theming** (M6.5 P1): `AppTheme` (GDScript, modelled on spritesheetbelli's) builds the `Theme` at startup from one palette per theme and the accent colour from Settings, and rebuilds it when the OS theme, the theme override or the accent changes. The app follows `DisplayServer.is_dark_mode()` and reacts to changes (use the system theme change callback if the pinned Godot version provides it; otherwise re-check on focus-in).
  - **Tokens:** background, surface, raised, hover, border, text, muted text, accent, error, plus the git colours (graph lanes, ref labels, added/removed/modified/renamed, diff backgrounds and highlights, syntax).
  - **Type variations** for the big header buttons, worktree chips, segmented toggles, section headers, toasts and the blocking overlay. Text on selected rows is checked for WCAG AA contrast against the accent.
  - This replaces `cargo xtask themes` and the generated `themes/*.tres`; AGENTS.md changes with it.
- **Icons** (M6.5 P1): Godot editor SVG icons (MIT, notice kept with the licenses) plus git icons drawn on the same 16 px grid in the same greys: branch, commit, merge, fetch, pull, push, worktree, shelf, tag, remote. They are recoloured for the light theme, and active icons take the accent colour.
- **Localization:** English source strings are keys in `godot/localization/gitbello.csv`, imported as Godot translations. `L10n` applies the persisted Settings → Interface → Language choice (System, English or Italian); System selects Italian for `it*` OS locales and English otherwise. Fixed app/core messages are translated at the UI boundary, while paths, refs, user content, Git commands/progress and raw stderr remain unchanged. Controls with dynamic text refresh on `NOTIFICATION_TRANSLATION_CHANGED`.
- **Menu bar:** a `MenuBar` with `prefer_global_menu`, so macOS gets the system menu bar where Godot supports it and the other platforms an in-window bar.
- **Export:** use custom export templates built with 3D and unneeded modules disabled to shrink the binary (M11).

### 3.8 Config and persistence

- User config lives in the OS config dir (`gitbello_core::paths`, written by hand; the `directories` crate's Windows dependency does not build on the GNU toolchain) as TOML:
  - known repos (until M7.5; then imported once into the library below and no longer written)
  - clone folder (M7.5; empty means the last clone's folder, `last_clone_folder`, then Documents)
  - open repo tabs, each with its selected worktree (saved worktree tabs from before M6.5 migrate to their repo's tab)
  - worktree path template
  - editor command (default `code {path}`)
  - terminal command (default: the platform's terminal)
  - pull mode (`ff-only` by default, `merge` or `rebase`)
  - auto-fetch interval
  - keybindings
  - theme override, interface language and accent colour
- Per-repo user state (last selected branch, panel sizes, the shared sidebar width) is stored in the app's data dir, keyed by the repo's canonical path. The repository library (M7.5) is `library.toml` in the same dir (`repos.toml` is the per-repo state): one `[[repo]]` per repository (`path`, optional `name`, `pinned`, `added`, `opened`, `root_commit`), unknown keys kept like the config; a broken file is set aside as `library.toml.broken` and the list starts empty, with a toast. **Never write to the user's repo**, except the optional repo-shared `.gitbello/actions.toml` that users create themselves.

### 3.9 History graph

- Stream `git log` in topological order, parsing commits as they arrive. Build a compact `GraphIndex` with commit table, parent indices and ref decorations.
- **Lane assignment** happens incrementally in core: a standard "active lanes" algorithm that assigns each commit a column and emits edge segments per row. Godot receives per-row `{column, color_idx, segments[]}`.
- **Memory target:** under 150 bytes per commit in the index, excluding strings. Interned author names and subjects are stored in an arena.
- **Performance targets** (M1 acceptance): about 80k commits (the `git/git` repo) fully indexed in under 2 s on a modern machine. The first screen appears within 300 ms (stream the first page). Scrolling holds 60 fps with no dropped frames. Idle CPU stays near 0%.

### 3.10 Diff, staging and editing

- Diffs come from git (`git diff`, `git diff --cached`, `git show`), parsed into hunks and lines in core.
- **Viewing:** the diff text is selected like plain text (drag, double and triple click, Shift, Ctrl+A, Ctrl+C; one side at a time side by side), not as highlighted rows; drags after a double or triple click go by words or lines, Shift+Left/Right extend it (Ctrl by words); Copy and Select all are actions in the diff's context menu and the Edit menu; the arrow keys move a line at a time and only they show a caret, and the lines a selection touches are what Space picks and Delete discards. Diffs load with `-U3`. The lines between hunks open GitHub Desktop-style: a hunk header's expanders show 20 more lines above it or below the previous hunk (all of a gap of 20 or fewer), each says how many lines it hides, an end row ("Show 47 more lines") opens the rest of the file, and **Show whole file** (`diff.toggle_whole_file`, the header's toggle) opens every gap. Core keeps the open gaps per diff (`Expansion`, kept across reloads of the same file) and builds a `DiffLayout` of runs (diff lines, a recounted header, unchanged lines, the end row); the unchanged lines come from the old side's blob (`git cat-file blob`, read in a job once a gap opens or when the last hunk may not reach the end of the file, up to 16 MB, a failed read not retried), since git's context lines come from that side too. `RepoSession.expand_diff(slot, gap, how)` and `show_whole_diff(slot, whole)`; diff rows of headers carry `gap`, `expand` and `hidden`, and unchanged lines have `index` -1; `diff_info` carries `can_expand` and `whole`.
- **Hunk and line patches:** build a minimal patch from the selected lines (recomputing hunk headers) and apply it with `git apply --cached --recount`. Unstaging uses `-R`. Discarding a selection applies the reverse patch to the working tree, after a confirmation, and stays immediate.
- **Commit selection** (M6.5 P3, D10): the file checkboxes and the hunk and line picks are a selection kept in core, one per worktree.
  - **Model** (`changes.rs`): each changed file has a pick: `Included`, `Excluded`, `AsStaged` (committed exactly as the index has it) or `Lines` (line keys). The checkbox shows all, none or partial. Line picks are keys, not rows, so they survive a reload of the diff: a removed line by its old line number, an added line by the old line it follows plus a hash of its text and its ordinal. Status keeps each file's index blob and mode (porcelain v2 `hI`/`mI`) for this.
  - **Seeding:** when the index has staged changes, the selection starts as exactly those; otherwise every change starts selected. Changes that appear later start selected. When a file's index blob changes from the one seen (staging outside gitbello), that file alone is reseeded from the index, so nothing staged elsewhere is silently dropped. A file staged in part starts `AsStaged`; when its diff opens, the staged lines are matched onto it and it becomes a `Lines` pick if every staged line matches, else it stays `AsStaged` with a note.
  - **Diff:** the Changes view shows the working copy against HEAD (`DiffKind::Head`; the empty tree before the first commit). Line picks and line discards use this diff. During amend, `DiffKind::Amend` compares the working copy with the original commit's first parent (its empty tree for a root commit), and `DiffKind::AmendStaged` compares the preserved selection snapshot with that parent; line picks use both, while line discard is unavailable. Discarding whole files always restores them from the real HEAD (index and working copy), backed up for Undo.
  - **Commit:** one write job builds the commit in a temporary index (`GIT_INDEX_FILE`), so the real index is never touched until the commit exists: `read-tree HEAD` (or the amend parent's tree); whole files with `add -A` (a staged rename takes its source); `AsStaged` files with `update-index --index-info` from the selection snapshot's blob; `Lines` files by re-reading the applicable diff, matching the keys and `apply --cached --recount` (a key that no longer matches fails the job before anything is written); then `commit -F -` (with `--amend` and `--allow-empty` when amending). Only then are the committed paths reset in the real index (`reset -q --`). A failing hook or a cancel leaves the real index as it was.
  - **Amend session:** `begin_amend` first writes the current selection to a temporary-index tree snapshot, preserving partial and overlapping changes without touching HEAD, the real index or working files. Its baseline and message come from HEAD; its change list merges the parent-to-working diff with the parent-to-snapshot diff. The ordinary selection is saved separately and restored on cancel. Status refreshes update the amend model from the fixed baseline and snapshot; a changed HEAD, branch or operation ends the session, and saving checks the expected HEAD and branch again in the write job. `cancel_amend` is local and immediate. `is_amending`, `in_amended_commit` and `amend_requires_force_push` feed the UI; the last uses known remote-tracking refs and upstream state.
  - **API:** `Runtime::{pick_files, pick_all, pick_lines}` change the selection in memory (no job) and send `SelectionChanged`; `select_change` loads the applicable Changes diff; `commit` commits the selection; `commit_block_reason` says why it cannot ("Nothing included", "Resolve conflicts first", "Write a summary"). `RepoSession` lists one change list (`change_count()`, `change_rows(start, count)` with `{path, original_path, code, pick, conflicted, as_staged, amending, in_original_commit}`, `change_paths`, `change_index`), `select_change(path, full)`, `pick_files(paths, include)`, `pick_all(include)`, `pick_lines(lines, include)` (a hunk header takes its hunk), `picked_count()`, `selection_state()` (the check-all box), `commit_block_reason(amend)` and the `selection_changed` signal; diff rows carry `picked`, `diff_info` carries `as_staged`. Staging calls (`stage_paths`, `stage_all`, `unstage_all`, stage and unstage `apply_lines`) leave the gdext API; `apply_lines("discard", …)` stays.
  - The selection lives in memory: after a restart it is seeded again from the index.
- **Editing in the diff viewer:** the working-copy side is editable. While the user types, core re-diffs the buffer against the index version in memory using `imara-diff`, so the view updates live without touching disk. Save writes the file, then the watcher confirms and git becomes authoritative again. Unsaved buffers are protected on tab close or refresh, and if the file changes on disk while dirty, the user is asked to reload or keep their version.
- **Large or binary files:** above a size threshold, show a summary with a "load anyway" option. Binary files show a size and type summary only, except images, which open in the image viewer (M7.8).

### 3.11 Undo (operation log)

- Before each undoable operation, core records an `OpLogEntry` with the HEAD, the affected refs (old to new), the stash list head, and a description.
- **Undoable:** commit, amend, branch create, delete or rename, checkout, cherry-pick, merge (before push), shelf discard (the dropped commit is kept), and reset.
- **Undo** restores the refs (`git update-ref` with the expected old value as a safety check). It refuses if the working tree is dirty and something would be overwritten, offering to shelve first.
- **Never undoable:** anything already pushed (warn instead), and changes to working-tree files that git never stored.
- The reflog is the fallback: an "advanced restore" view lists recent reflog entries.

### 3.12 Custom actions

- Actions are defined in user config (global or per repo) and optionally in a repo's `.gitbello/actions.toml`.
- Each action has a `name`, `command`, `cwd` (repo, worktree or file dir), `confirm`, and `show_output`.
- **Variables:** `{repo}`, `{worktree}`, `{branch}`, `{file}`, `{commit}`.
- Actions are registered in the `ActionRegistry`, so they appear in the palette and context menus.
- **Trust:** actions from a repo's `.gitbello/actions.toml` are untrusted until the user approves them for that repo. If the file changes, approval is required again (similar to VS Code workspace trust).
- **Worktree setup hook:** the new-task flow can run a chosen action after creating a worktree, for example copying `.env` or installing dependencies.

### 3.13 Integrated terminal (M10)

Embedding a real terminal needs three pieces: a PTY (`portable-pty`, which uses ConPTY on Windows), a terminal state machine (`alacritty_terminal` or `vte`), and a grid renderer in Godot (`_draw()` with a monospace font, cursor, selection and scrollback). It is a substantial component, so it comes last.

**Fallback (ships in M5):** an "Open terminal here" action that launches the user's configured terminal in the active worktree.

**Window layout.**

**Menu bar.** Built from the action registry; disabled items say why in their tooltip. The top row uses compact 13 px text; dropdowns stay at 14 px. F10 opens File on Windows/Linux, and Alt plus the localized menu's initial opens a menu; native macOS menus keep platform behavior.
- **File:** Home, Open repository…, Open recent (including open repositories), Clone…, Scan folder…, New repository (Create… and Initialize folder…), Close tab, Settings (Ctrl+,), Quit.
- **Edit:** Copy, Select all, explicit Undo operations, Find and search matches.
- **Repository:** Fetch, Pull, Push, New worktree, worktree management, Open terminal / file manager, Remotes and tags, Shelves, operation commands only while one is in progress, Refresh.
- **Branch:** Switch…, New branch, Merge into current…, Rename, Set upstream.
- **View:** checked Changes / History / Shelves choices, checked diff and Git log toggles, Command palette. Themes live in Settings and remain palette actions.
- **Help:** Keyboard shortcuts, About.

**Repo tabs.** One tab per repo, never per worktree; the title is the repo name.
- An attention dot shows the most important state across the repo's worktrees: conflict or operation in progress (error colour), then changed files (modified colour), then ahead/behind (accent). Its tooltip lists each worktree with its state.
- A small spinner shows while any job of the repo runs.
- The tab-strip **+** opens the Home page in a Home tab (see **Home** below; until M7.5 it opened one Add repository window with create, open existing and clone).
- Opening a linked worktree's path (open dialog, recent list, command line, drag and drop, restored tabs) focuses its repo's tab and selects that worktree's chip.

**Home** (M7.5, settled in the Q&A of 2026-10-31). One page for finding, opening and adding repositories. It fills the window when no tab is open (replacing the welcome screen) and opens as a Home tab from the tab-strip **+** or Ctrl+N. There is at most one Home tab: **+** focuses it when it exists. Choosing a repository turns the Home tab into that repository's tab, or focuses its tab and closes Home when it is already open. Home tabs are not saved with the open tabs.

- **Filter field**, focused when Home opens: matches names and paths in any case. Enter opens the first match, ↑ ↓ move through the list, so opening a repository is one keystroke away.

**Feedback.**
- **In place:** the control that started a job (a big button, a chip, a row) shows its progress and is disabled until the job ends. Cancellable jobs cancel from the control's ▾ or with Esc.
- **No origin** (palette, shortcut, menu): a progress toast that shows the job and closes when it ends, or turns into its success toast when it has one. Auto-fetch stays silent unless it fails (one report per failure streak, as now).
- **When a success toasts:** only when it offers an action (Undo, Open) or nothing on screen shows the result. Results the UI already shows get no toast: commit and amend (the undo strip), sync, pull and push (the Sync button and counts), checkout (the branch button), merge, continue, skip, abort, resolve and undo commit (the banner, resolver, history or Changes), cherry-pick, worktrees (the chips), shelf restore and rename, tags and remotes (the list acted on), and Home's add and relocate (the cards). Toasts stay for discards (Undo), removing a repository (Undo), a finished clone (Open), copying a hash, shelving (the files leave the list), pushing a tag, and branch create, rename, delete and upstream changes made from the closed branch popover.
- **Toasts** are compact cards stacked at the bottom right of the content area: an icon for the kind (a green check, a red warning, a spinner), the text, inline action buttons in the accent colour and a close button; successes have a thin line showing their time left and fade in and out. The stack is bounded to one-third of the content's height (at most 280 theme units) with scrolling and an overflow count. Capacity never evicts errors, Undo or progress; hidden actionable notifications pause their remaining lifetime until exposed. Successes are short ("Copied 1a2b3c4") and hide after 6 s, or 12 s when they offer Undo. Their remaining lifetime pauses while hovered or while keyboard focus is anywhere inside that toast. Errors stay until dismissed and offer the classified fixes and Details (opens the git log at that command). An Undo button appears only where undo really exists: discard restore now, shelf discard from P4, and more with the operation log (M9).
- **Blocking overlay:** dims only the affected worktree's panes; the chips and other tabs stay usable. It is for writes that change that worktree's files and must finish before more input makes sense (checkout, pull, merge, rebase, cherry-pick, shelve, restore). It appears after 300 ms, shows what runs and its progress, and offers Cancel where git allows. The main thread never blocks (rule 4): the overlay only blocks input.

**Changes view.** One list of changed files with checkboxes: [x] included in the commit, [ ] left out, [-] partly included (some hunks or lines). The selection is gitbello's own (D10, §3.10).
- The header reads "N changed files" with a check-all box. Space toggles the checkboxes of the highlighted rows.
- Right-clicking the changed-file header offers Shelve all and Discard all. These actions cover every file currently shown, independently of highlighting and commit checkboxes; hidden files are untouched when filtering. Shelving asks for a name, discarding is confirmed and undoable. There is no separate Shelve action row.
- A filter above the header (Ctrl+F), like GitHub Desktop's: a text box matching paths in any case, and options for files included in or excluded from the commit and for new, modified or deleted files. While it hides files the header reads "2 of N changed files" and the check-all box covers the files shown. The options menu has a separate "Clear all filters" action below a divider, shown only while search text or an option is active; it clears both together. Escape still clears only the text. The filter lives in core (`ChangeFilter`), so rows stay in Rust.
- Row highlighting (click, Shift, Ctrl) is separate from the checkboxes. It drives the diff and the context menu: Discard…, Shelve…, Open, Show in file manager, Copy path, Ignore.
- The diff gutter has hunk and line checkboxes.
- The commit box sits under the list: summary, description, and a "Commit 2 files to main" button (Ctrl+Enter), disabled with a tooltip reason when nothing is included or the summary is empty. Amend is entered from the HEAD commit's History context menu ("Amend…", Ctrl+Shift+A), not a persistent checkbox. It opens the full proposed commit against its first parent (the empty tree for a root commit), loads its message, and temporarily shows "Amending “<commit summary>”", Cancel, and "Save amended commit". Original changes start included; existing working selections, including partial and overlapping changes, are preserved through a temporary-index tree snapshot. HEAD, the real index and working files are not changed by entering or cancelling amend. Unchecked files/lines remain in the working tree but are omitted from the replacement commit; unchecking everything can create an empty replacement commit. Cancel restores the ordinary draft and selection without undoing file edits; success restores the draft and returns to ordinary Changes. Discard explicitly restores working content to the original HEAD, not the amend baseline; line discard is unavailable in the parent-relative diff. Known pushed commits show a persistent force-push warning and require confirmation on Save. Saving uses `--amend`, preserving authorship and merge parents; a stale HEAD is rejected.
- **Empty state:** "No local changes" with big suggested actions for what makes sense now: Push ↑N or Pull ↓N when relevant, Open terminal, New worktree. (Until M7.5 the welcome screen followed the same pattern; it is replaced by Home.)

**Deleting branches** (approved 2026-11-07). One dialog, which first reads what the branch would lose (`load_branch_delete_info`: commits the base lacks, commits not pushed, its remote branch, its worktree), so an unmerged branch is deleted in one step with the loss shown, not refused and asked again:
- The dialog lists what goes as rows (`FormDialog.add_item`): a check box, an icon (branch, worktree folder, remote, tag), the name in a chip and short facts at the end, warnings amber ("2 commits not in main · 1 not pushed") and "merged into main" green. What the dialog is about is a fixed, ticked row; the others can be unticked. No "Delete X?" sentence: the title says it. Delete dialogs are narrow (`narrow_width`).
- The remote branch's row shows while the remote still has the branch: ticked, unless the branch has commits the base lacks (deleting both would lose them). Not remembered.
- The branch checked out here can always go: in the main worktree it switches to the base's local branch first (the usual switch, asking about local changes); in a linked worktree it deletes the worktree with it and the main one shows. A branch checked out in another linked worktree goes with that worktree. It cannot go while it is the base's branch checked out here, or checked out in the main worktree; the action says why.

The toast offers Undo: the local branch at its commit, the remote branch pushed back with a plain push (never over commits pushed since), the upstream. A worktree's folder does not come back.
- Delete remote branch… on remote branches ("gone for everyone"), offering the local branch that tracks it (ticked when it has nothing the remote lacks). Delete tag offers its remote, off.
- Clean up lists a row per worktree (merged or upstream gone, and what it would lose) with two toggles, Branches and On origin; Delete counts the ticked rows. The toast says "Deleted x here and on origin".

**Merge with preview** (M7, Q&A 2026-10-31).
- **Scope:** merge into the current branch only (the active worktree's branch). Rebase has no action yet; a rebase in progress (from Pull and rebase or the CLI) gets banner support only. Dragging a branch onto another comes later.
- **Entry points:** the branch popover's row menu (Merge into current…), Branch → Merge into current… and the palette (a filterable branch picker), and the graph menu of a commit or ref label, shown only when that commit is not in HEAD (graph rows carry `in_head`, from `rev-list --branches --remotes --tags --not HEAD`, loaded with the graph).
- **Preview** (a read job, nothing touched): `merge-tree --write-tree --name-only -z --messages HEAD <ref>` (exit 1 means conflicts), `rev-list --count` and the first 50 commits of `HEAD..<ref>`, `merge-base --is-ancestor` for fast-forward, and the merged files intersected with the local changes. Remote-tracking refs are used as of the last fetch.
- **Dialog:** "Merge feature/login into main", then "✓ No conflicts · 3 commits · 12 files changed" or "Conflicts in 2 files: a.rs, b.rs", a collapsible commit list, an editable message prefilled with git's default (hidden when it will fast-forward), and Cancel plus a split button whose label says what will happen:

| Case | Primary | ▾ |
|---|---|---|
| Fast-forward possible | Fast-forward main | Always create merge commit · Squash into one commit… |
| Diverged, clean | Create merge commit | Squash into one commit… · Fast-forward only (disabled, with the reason) |
| Conflicts | Merge and resolve… | Squash and resolve… |
| Nothing to merge | (Close only) "Already up to date" | — |

- **Local changes:** when they overlap the merged files, the dialog warns and the primary becomes "Shelve changes and merge" (an automatic shelf, the merge, then a restore after a clean merge; after a conflicting merge the shelf stays and the Changes view offers it back once the merge is committed or aborted). Changes that don't overlap stay put and are not part of the merge commit.
- **Running:** `merge` with `--ff` / `--no-ff` / `--squash` / `--ff-only`, the message without an editor, and `-c merge.conflictStyle=zdiff3` so the base is in the markers. It blocks the worktree (overlay). Conflicts open Changes with the first conflicted file in the resolver.

**Operation banner** (M7). "Merging feature/login into main · 2 of 3 conflicts left" (cherry-pick: "Cherry-picking abc1234 'subject'"; rebase: "Rebasing fix onto main · commit 2 of 5"). Buttons:
- **Continue**, disabled until no conflict is left. Merge and cherry-pick: the same as the commit box's button. Rebase: `rebase --continue` with no editor.
- **Skip** (rebase only).
- **Abort**, always confirmed; the confirmation says how many resolved files go back.
- **Open resolver**: selects the first unresolved file in Changes.

**Finishing a merge or cherry-pick in Changes.** The commit box is prefilled from `MERGE_MSG` (a cherry-pick keeps the original author) and reads "Commit merge into main" / "Commit cherry-pick". The checkboxes are locked: the commit takes the index (git's result plus resolved files), so local changes that were there before the merge stay out. During a rebase the commit box is disabled ("Use Continue in the banner"). A squash merge is not an operation: its staged result is committed like any other change, with a message built from the squashed commits prefilled.

**Conflict resolver** (M7). It lives in the Changes view: conflicted files are listed first, and selecting one shows the resolver in the diff pane. Unified or Side by side follows the diff header's toggle (the same remembered setting).
- **Unified:** the file with each conflict as a block: a header "Conflict 1 of 3 · [Ours] [Theirs] [Both ▾]" (Both: ours then theirs, or theirs then ours), then the ours lines and the theirs lines labelled with their branch.
- **Side by side:** ours on the left and theirs on the right, aligned per block, with Take ours · Both ▾ · Take theirs in the block header.
- **Show base:** a toggle that adds the base section to each block (full-width rows side by side). It needs zdiff3 markers. For a conflict made outside gitbello without them, it offers "Recreate conflicts with base" (`checkout --conflict=zdiff3`, confirmed if the file was edited).
- **Choices** rewrite that block in the working file (line endings kept); Ctrl+Z undoes block choices while the file is unresolved. Hand edits go through Open (the default app, M7.8 P3); the file reloads through the watcher.
- **Resolving:** a file is staged (`git add`) as soon as no markers are left, whether that came from choices or from an outside edit. The file list shows the progress ("2 of 3 resolved"); a resolved file's menu offers Reopen conflicts (`checkout -m`, confirmed).
- **Non-text conflicts** show a card instead of blocks:
  - Modify/delete: Keep the file (the modified side) or Delete it.
  - Binary: Use ours or Use theirs, with sizes.
  - Add/add: blocks when both sides are text, otherwise pick a side.
  - Renames: pick a side.
- Conflicts are read from `ls-files -u -z` and the working file's markers; stage blobs come from `cat-file blob :1:<path>`, `:2:` and `:3:`.

**Undo commit strip** (M7, GitHub Desktop style). Under the commit button: "<subject> · committed 3 min ago · Undo" for HEAD while it is unpushed (not on its upstream; with no upstream, not on any remote branch). It is hidden during an operation.
- **Undo:** `reset --mixed <first parent>` after checking that HEAD is still that commit. The commit's changes join the local changes and its message fills an empty commit box. The next unpushed commit then shows, so several commits can be undone in a row into one set of changes. The first commit of a branch makes the branch unborn again (`update-ref -d`).
- **Undoing a merge commit** asks first: **Undo, keep changes** (as above: everything merged becomes local changes and the merge is lost) or **Remove merge** (`reset --keep <first parent>`: the merged changes are not brought back, since they are still on the other branch; local changes are kept).
- Fast-forwarded commits show as ordinary commits.

**Shelves** (M6.5 P4, D11; replace the classic stash workflow).
- A shelf is a git stash (untracked files included) whose message is `gitbello-shelf: <branch>: <name>`. It is identified by its commit, never by `stash@{n}`, because the stash stack is shared by every worktree and its indices shift.
- A shelf belongs to its branch and shows in any worktree that has that branch checked out. Stashes made elsewhere are listed too, with the branch read from git's `WIP on <branch>:` / `On <branch>:` message.
- **Shelve:** highlight files, then right-click → Shelve… and name it; right-click the changed-file header to shelve every currently listed file. Whole files only for now; hunk and line shelving comes later, since `git stash push -p` is interactive and needs a temporary index plus `git stash store` instead.
- **Shelves view** (approved 2026-10-26, refined 2026-10-27): replaces the inline Shelved section. The left list contains shelf names under collapsible branch headings (current branch first and the only group expanded on load), without shelf expansion or a repeated page heading. Refresh preserves group choices; collapsing the selected shelf's branch keeps its details visible. A name filter includes a branch picker supporting any subset or all branches, with the shared count badges. Selecting a shelf shows History-style details and a separate file list beside the diff on the right. Clicking the name or invoking Rename edits the name inline: Enter or leaving the field saves, Escape cancels, and an empty name keeps the original. There is no rename dialog. Restore and Discard use quiet icon/text buttons at the far right of the name row, with error-colour hover feedback for Discard. Filtering away the selection hides the entire right content area and its actions; the empty-filter reason appears only in the left list. The preview works with a clean working copy and has no commit checkboxes. The navigation button counts shelves across the repository and hides at zero, returning to Changes if Shelves was active. Restore applies then drops on success (conflicts keep the shelf); Discard is confirmed and its toast offers Undo. Renaming the newest shelf temporarily protects its commit under `refs/gitbello/rename-shelf/<oid>` while replacing the top stash entry, with rollback if storing the new name fails; older entries use store-then-drop.
- **File actions** (API approved 2026-10-27): right-click a shelved file to Restore file or Discard file. Restore moves only that file to the working copy, preserving unrelated staged work through a temporary HEAD index; it refuses existing local edits on the selected paths. Discard is confirmed and offers Undo, which replaces the remainder with the original shelf without duplication and refuses a remainder that changed or disappeared. Renames include their source path, index-only files remain visible and preview their staged content, replacement shelves keep their name/branch/date, and removing the final file drops the shelf. `restore_shelf_file(oid, path)` and `discard_shelf_file(oid, path)` are worker jobs; `shelf_replaced(old_oid, new_oid)` keeps UI selection on the remainder (empty new ID means removed). All shelf writes use a shared lock across worktrees; original commits are protected for recovery and partial-discard Undo. See `docs/SHELF_FILE_ACTIONS.md`.
- **Switching branch with changes** asks: **Bring them to feature** (the stash, switch and re-apply flow from M5) or **Leave them on main** (an automatic shelf, then the switch). When a worktree is on a branch that has automatic shelves, the Changes view offers them back: "3 changes were left on main · Restore".
- **API** (approved 2026-10-25). Core: `Shelf { oid, branch, name, auto, made_here, time }` built from the stash list (`shelves()`; automatic shelves are `gitbello-shelf (auto): <branch>: <name>`; other stashes have `made_here = false`), and `ShelfFile { path, original_path, code, untracked }`. Every write looks the stash index up by commit right before it runs. Shelve is `stash push --include-untracked -m … -- <paths>`; Restore is `stash apply --index <oid>` (without `--index` when the staged part does not apply), then a drop on success, so a conflicting restore keeps the shelf; Rename is `stash store -m <new> <oid>` then a drop of the older entry; Discard drops it and remembers commit and message for Undo (`stash store`, for the session). Runtime jobs `shelve`, `restore_shelf`, `rename_shelf`, `discard_shelf`, `undo_shelf_discard` (shelve and restore block the worktree), `load_shelf_files` (event `ShelfLoaded`), `select_shelf_file` (a preview in the Changes diff, no checkboxes), and `checkout(key, target, changes)` with `Keep`, `Bring` or `Leave` (an automatic shelf, then the switch; the changes come back if the switch fails). `RepoSession`: `shelves()`, `load_shelf_files(oid)`, `shelf_files_loaded(oid)`, `shelf_files(oid)`, `select_shelf_file(oid, path, full)`, `shelve(paths, name)`, `restore_shelf(oid)`, `rename_shelf(oid, name)`, `discard_shelf(oid)`, `can_undo_shelf_discard()`, `undo_shelf_discard()`; `checkout_branch`, `checkout_remote` and `checkout_commit` take `changes` (`keep`, `bring` or `leave`) instead of `stash`. Switching with changes always asks; the return offer restores the newest automatic shelf.

**Command palette.** `Ctrl/Cmd+K` (and `Ctrl/Cmd+Shift+P`) opens a fuzzy search over all actions, branches (to check out), repos and their worktrees (to switch), and files (to open their diff). With no search text, it lists only available commands. A search also reveals unavailable commands, dimmed with a compact hint and the full disabled reason in a tooltip. Hints wrap rather than being truncated when space is tight. Unavailable rows cannot be selected or executed, and keyboard navigation skips them. ### M7.6 — Content navigation: autoscroll and the diff minimap (≈1.5 weeks)

Scope settled in the Q&A of 2026-11-01. Two independent parts, each ending with a review stop: P1 middle-click autoscroll everywhere, P2 a VS Code-style minimap in place of the diff's scroll bar.

**P1 — Middle-click autoscroll.**
- **Behaviour** (browser-style, every OS, no setting): a quick middle click (released within ~250 ms without leaving the dead zone) starts sticky autoscroll; holding the button and moving scrolls only while it is held. An anchor icon stays at the click point, the cursor shows the direction (`CURSOR_VSIZE`, `CURSOR_HSIZE` or `CURSOR_MOVE`), and speed grows with the distance past a dead zone (~8 px, HiDPI-scaled; about `k · d^1.5`, capped). Only the axes that can scroll take part.
- **Stops on:** any mouse button (consumed), a wheel turn (which then scrolls normally), Esc (consumed), any other key (passed on), focus loss, or the target hiding or leaving the tree.
- **Where:** every `VirtualList` (change lists, shelf files, commit list and graph, `DiffView` on both axes) and every `ScrollContainer` (Home, Settings, shelves, scan dialog, worktree list popover, toasts, the worktree strip sideways). Controls with their own middle click (a worktree chip shows its folder) accept the event first, so autoscroll only sees the unhandled ones.
- **Shape:** one `AutoScroll` node (a `CanvasLayer` on top) per window, in `godot/ui/auto_scroll/`. It reads middle presses in `_input`, before the controls (a press over a control with `MOUSE_FILTER_STOP` never reaches its `ScrollContainer` parent), walks up from the hovered control and starts on the first `VirtualList` or `ScrollContainer` that can scroll; a control in the `own_middle_click` group (the worktree chip) or a text field ends the walk. `AutoScroll.enable(control)` adds the window's instance: `VirtualList._ready` calls it, and so does each place that makes a `ScrollContainer`. `VirtualList.scroll_axes()` and `scroll_by(delta)` are what it drives; `DiffView` adds the horizontal axis. While running it swallows mouse motion (no hover effects), draws the anchor icon and moves the offsets in `_process`; nothing runs while it is idle. Dead zone and speed are theme constants in `app_theme.gd`; `AutoScroll`, `AutoScrollVertical` and `AutoScrollHorizontal` SVG icons (`LICENSES.md`).

**P2 — Diff minimap** (Changes, History and the resolver; every `DiffPanel`).
- **Layout:** a column of about 100 px (theme constant, HiDPI-scaled) replaces `DiffView`'s vertical scroll bar; the horizontal scroll bar stays. On its right edge, a strip of ~6 px always covers the whole diff.
- **Preview:** rows of the diff as shown (a collapsed gap is its header row, drawn with a thin dashed divider when it hides lines), 2 px per row, one block of about 1 px per character, syntax-coloured, on the row's background: added, removed, hunk header, unchanged; in the resolver ours, theirs and base in the sides' colours. Lines left out of the commit (Changes, `pickable`) are dimmed. Side by side: one column, old side in the left half, new side in the right half, row for row.
- **Scrolling** (VS Code's proportional mode): while the rows fit, the minimap is drawn from the top at 2 px per row; past that it scrolls along so its offset is the diff's scroll ratio times its overflow. A translucent viewport box marks the visible rows: drag it to scroll, click outside it to centre that row, wheel over the column scrolls the diff. Middle-click autoscroll works over it as over the diff.
- **Edge strip:** marks for the whole diff, one bucket per pixel: unresolved conflict blocks first, then removed, added and left-out lines (a block choice turns a conflict into plain lines, so a chosen block simply stops being marked); the selection as a faint band (drawn in GDScript from `DiffView`'s selection); a shade for the visible rows. Clicking the strip jumps there.
- **Off or narrow:** the setting **Show minimap** (Settings, on by default, `diff_minimap` in `config.toml`) and the action `diff.toggle_minimap` (palette, diff context menu, View menu). Off, or when the diff is narrower than ~600 px, only the strip stays, widened to a scroll bar with a thumb, so the change marks never go away.
- **Data stays in core** (approved 2026-11-01). Core renders the preview in tiles of 256 rows straight into RGBA bytes, with the colours GDScript passes from the theme, and computes the strip's buckets; GDScript wraps tiles in `ImageTexture`s, keeps a few (LRU) and drops them on a diff change, pick change, expand, side-by-side toggle, theme or accent change. Scrolling only draws cached textures.

### M7.9 — Line endings (≈1 week)

Scope settled in the Q&A of 2026-11-07. Today a missing final newline is the text `\ no newline at end of file` appended to the last line (code colour, selectable), and a trailing `\r` is dropped before drawing, so a CRLF ↔ LF change reads as identical red/green pairs. Two parts, each ending with a review stop. Applies to every text `DiffPanel` (Changes, History, Shelves; the resolver keeps endings as it does). Out of scope: a hide-whitespace or ignore-endings toggle, `core.autocrlf` / `.gitattributes` (read, shown or edited), Convert to LF/CRLF, add/remove final newline, conflicts.

**Terms.** A line's *ending* is LF, CRLF, or none (the last line without a newline), as git compares them: after its clean filter, so a repository that normalizes endings (`autocrlf`, `text`/`eol` attributes) produces no ending changes and none of what follows shows. A side's endings over some lines are `LF`, `CRLF` or `Mixed`.

**P1 — Showing them.**
- **No newline row:** the line without a final newline is followed by a row of its own, drawn like a hunk header (changed at the second review): "No newline at end of file", no line numbers, no checkbox. Unified: after that line; split: on its side only. The `\ no newline` text appended to the line goes.
- **Line endings row** (changed at the first review): when endings changed, one row like the no-newline one after the diff's last line (after the lines Show whole file opens, before the end row's expanders): "Line endings: CRLF → LF (3 lines)" (`LF`, `CRLF` or `Mixed` per side). Endings changed where a change block's removed lines' endings differ from its added lines' (an insertion: from its hunk's unchanged lines); it also covers lines whose text changed. The -/+ lines stay as they are, so staging is unchanged. Split: the row spans both sides.
- **Marker rows** are core layout rows (new kinds; golden rule 6), drawn muted at the line height; they are skipped by selection, Copy, Select all, F7 navigation and the minimap, and kept in Show whole file.
- **No header chip** (dropped at the first review): the row at the end says it.
- **Card:** a file whose only changes are endings and/or the final newline shows a card instead of the diff, like the binary summary, each change on a line of its own (changed at the second and third reviews): "Line endings: CRLF → LF (342 lines)", "Newline added at the end"/"Newline removed from the end", with **Show diff** (this file, this session, as Load anyway) and, in Changes on the working copy, **Restore line endings** (P2). History and Shelves show it with Show diff only.

**P2 — Restoring them.**
- **Restore line endings** (`changes.restore_line_endings`, list and diff context menus, the card, the palette): for each selected file in Changes with ending changes between the index and the working copy, rewrite the working file so changed lines take the endings the index version had, keeping their text: an added line paired by position with a removed line takes its ending, other added lines the block's (else the file's) old ending; the final newline goes back to the old state when the last line's text is unchanged. A core write job; the files' contents are backed up first (`hash-object -w`) and pushed on the discard undo stack, so the toast offers Undo and Edit → Undo discard covers it. No confirmation. Staged-only changes and untracked files are not touched.
- **Line-ending-only files in the list:** after each status refresh, a read job (`git diff --numstat --ignore-cr-at-eol` against the index, through `GitRunner`) finds the modified text files whose changes are endings only; the Changes list shows a small `EOL` chip on them. The list's filter menu gains **Line endings only**; with it on, select all and Restore line endings restores them in one go.

- **Godot:** action `changes.restore_line_endings` (list and diff context menus, palette, the card's first button in Changes; History and Shelves keep Show diff only); toast "Restored line endings in …" with Undo (`changes.undo_discard`). `FileRowPainter` draws the `EOL` chip (`ChangeList` `chip_color`, `chip_bg`, `chip_font_size`, `chip_radius`), with "Only line endings changed" in the row tooltip; the list filter gains "Line endings only".
- **Tests:** `diff/eol.rs` restore unit tests (paired, text kept, mixed, insertions, final newline both ways, stale); `tests/line_endings.rs` (restore + undo with a non-ASCII path with spaces and an untracked file left alone, staged-only changes start no job, the scan with 3 ending-only files and 1 real change plus the filter); `line_endings_smoke.gd` (chips, filter, card buttons, enabled state, restore from the card and Undo). ## 6. Testing strategy

- **Parser unit tests:** captured git output fixtures, including unusual cases (renames, copies, unmerged entries, submodules, unicode paths, CRLF).
- **Integration tests:** real temp repos created with the fixture builders, with local bare repos standing in as remotes. Every operation in `CliBackend` gets at least one success test and one failure test.
- **Scheduler tests:** ordering, coalescing and cancellation, using a fake backend.
- **Smoke tests:** headless Godot scripts that load the main scene, open a fixture repo, and assert on the tabs, worktree chips, lists and badges.
- **Performance check:** a CI-optional benchmark (`cargo xtask bench-graph <path>`) that records results in `docs/perf.md`.
- **Manual test scripts:** written at the end of every milestone for Caleb.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Godot UI too slow or awkward for large lists and text | M1 spike is a go/no-go checkpoint; keep core UI-agnostic so a different frontend stays possible |
| gdext API changes (pre-1.0) | Pin versions; keep the boundary small (`gitbello-gdext` only) |
| git output differences across versions or platforms | Minimum version check, `-z` formats, `LC_ALL=C`, fixture tests in CI on all three OSes |
| Line-staging bugs corrupting the index | Extensive patch-construction tests; verify with `git apply --check` before applying; undo log |
| Commit-time staging losing work staged elsewhere | Selection seeded from the index and reseeded on outside changes; the commit is built in a temporary index, so the real index changes only after the commit exists; tests for outside staging and failing hooks (M6.5 P3) |
| The UX refresh breaking smoke coverage | Smoke tests rewritten inside each phase, not after; screenshots reviewed at every phase review |
| Scope creep | Out-of-scope list in §1; milestone reviews; daily-driver checkpoint at M6.5 |
| Terminal effort | Fallback external terminal ships early in M5 |
